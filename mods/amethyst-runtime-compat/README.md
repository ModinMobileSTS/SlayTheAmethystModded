# Amethyst Runtime Compat

This mod carries runtime-side compatibility fixes that are safer to ship as ModTheSpire patches than as direct game-jar edits.

## Source package layout

The root package only contains the ModTheSpire initializer. Runtime fixes should live in the package that matches their ownership boundary:

- `io.stamethyst.compatmod.core`: shared runtime configuration and state used by multiple fixes.
- `io.stamethyst.compatmod.bridge`: launcher/JVM bridge helpers.
- `io.stamethyst.compatmod.ui`: base-game UI, scaling, settings, and menu presentation compatibility.
- `io.stamethyst.compatmod.touch`: native-touchscreen and touch-card-input behavior.
- `io.stamethyst.compatmod.rescue`: save/room/render rescue fallbacks for corrupted or incomplete runtime state.
- `io.stamethyst.compatmod.diagnostics`: diagnostic and memory-observation hooks.
- `io.stamethyst.compatmod.lifecycle`: expected-exit and process-lifecycle markers.
- `modCompatibility`: compatibility fixes scoped to a specific external mod.
- `io.stamethyst.compatmod.autoplay`: harness-only autoplay and single-room automation.

## Included fixes

Startup cache and cache-hit-only performance strategies are summarized in
`../../docs/mts-startup-cache-strategies.md`; the entries below still document the
individual runtime patch classes for this mod.

1. `FontScaleCompatPatches`
Adjusts `FontHelper.prepFont` so launcher-configured text scaling is applied consistently during MTS launches while staying independent from the launcher UI-scale slider. This addresses the symptom where text sizing only followed the base game's `Bigger Text` behavior or got unintentionally magnified again when UI scale was increased. Type: compatibility workaround implemented by `FontScaleCompatPatches`.

2. `ResolutionDropdownCompatPatches`
Guards the in-game settings resolution dropdown on Android-compatible runtimes. When no desktop-compatible resolution list can be built, the dropdown is replaced with a single `N/A` entry and resolution changes become a no-op instead of crashing. The patch also normalizes stale dropdown selection and scroll-window state during settings rendering so toggling graphics options cannot leave the placeholder dropdown pointing past its only row and crash inside `DropdownMenu.layoutRowsBelow`. Type: crash fix implemented by `ResolutionDropdownCompatPatches`.

3. `DuelistCompatPatches`
Short-circuits a few Duelist dynamic/base-value lookups so they reuse current card state instead of going through slower or less stable reflection-heavy paths.

4. `CharacterPreviewReuseCompatPatches`
Adds hooks used by `RuntimeMemoryDiagnostics` to track main-menu and character-select preview lifecycle, including preview reuse for modded characters and per-selected-character recreate summaries when the menu has to rebuild a modded preview instead of reusing it.

5. `RuntimeMemoryDiagnosticsPatches`
Adds runtime hooks for update/create-character/start-over/reset/dispose so memory diagnostics can observe long-session behavior without modifying the base game directly, including menu-cycle texture/FBO summaries and owner/source hotspot attribution suitable for diagnostic play sessions. All `[amethyst-runtime-diag]` startup, summary, verbose, hotspot, and GPU-summary failure logs are silent unless the launcher's `amethyst.gdx.gpu_resource_diag` property is enabled, addressing the symptom where runtime diagnostic logging could appear during normal launches even when GPU diagnostics were disabled. Type: diagnostic hook implemented by `RuntimeMemoryDiagnosticsPatches` with logging controlled in `RuntimeMemoryDiagnostics`.

6. `FrierenTextureCacheCompatPatches`
Intercepts `ImageMaster.loadImage` for Frieren slot-library textures and reuses one `Texture` per resource path instead of letting `Slot`, `SlotBgLibrary`, and `refreshSlot()` repeatedly allocate duplicates. This targets the severe GPU-memory growth that happens when Frieren rebuilds the full slot background library on each return to the main menu. Type: compatibility workaround for a third-party texture leak.

7. `DownfallMainMenuAtlasCompatPatches`
Intercepts `downfall.patches.MainMenuColorPatch.setMainMenuBG(TitleBackground)` and reuses a singleton Downfall main-menu `TextureAtlas` instead of constructing a fresh atlas on every menu rebuild. This targets the repeated `title.atlas` / `title.jpg` GPU-memory leak seen when bouncing back to the main menu. Type: compatibility workaround for a third-party texture leak.

8. `HinaCharacterRenderCompatPatches`
Downsizes Blue Archive Hina's offscreen 3D character render target from its desktop-style supersampled framebuffer to a mobile-safe framebuffer, keeps the helper's original logical camera scale, and replaces the original mipmap generation path with linear filtering during the final blit. It also caches reflected helper fields/methods, reuses the framebuffer `TextureRegion`, moves final-blit filter setup to framebuffer creation, and throttles render fallback logging so the compatibility path does not add per-frame reflection/allocation/logging overhead. This addresses the symptom where Hina's in-run 3D model renders as a blank character or at the wrong size on Android-compatible runtimes after the oversized framebuffer is pressure-downscaled or the desktop mipmap path misbehaves, while avoiding frame-time spikes from the workaround itself. The fix is controlled by the launcher's runtime compatibility switch for Hina character rendering. Type: compatibility workaround and performance fix for third-party mobile rendering assumptions implemented by `HinaCharacterRenderCompatPatches`.

9. `UiScaleCompatPatches`
Uses the launcher's UI-size setting to dynamically rewrite base-game and mod reads of `Settings.isMobile`, so enlarged mobile-style layout branches are reused without turning on the real mobile HUD mode. Main-menu classes and speech-bubble VFX classes are intentionally excluded so the title screen and dialogue bubbles keep their desktop behavior instead of picking up mobile-only spacing and text placement. This addresses the symptom where the only built-in way to enlarge the interface was the native mobile HUD toggle, which also changes global runtime state and can break modded screens. Type: compatibility workaround implemented by `UiScaleCompatPatches` together with `MobileUiLayoutClassPatcher`.

10. `BurningEliteFlameCompatPatches`
Enlarges the burning-elite emerald flame marker when the launcher's Larger UI mode reuses mobile map-node scaling. This addresses the symptom where the elite node grows with the larger mobile-style layout but its flame VFX stays at desktop size and becomes hard to notice. Type: compatibility workaround implemented by `BurningEliteFlameCompatPatches`.

11. `CharacterOptionRelicKeywordCompatPatches`
Reapplies BaseMod's starter-relic multiword-keyword normalization when mobile layout handling is active inside `CharacterOption.renderRelics`. This addresses the symptom where character-select relic descriptions leak raw keyword prefixes such as `spearandshield:` after the launcher's Larger UI mode reroutes the screen through the mobile single-relic branch. Type: compatibility workaround implemented by `CharacterOptionRelicKeywordCompatPatches`.

12. `JacketNoAnoKoElectrocardiogramCompatPatches`
Rewrites JacketNoAnoKo's `ElectrocardiogramLoeweEffect` shader sources to GLES 100 at runtime on Android-compatible runtimes, installs the compiled shader back into the original effect, and lets the original render method draw the visual effect. If the rewritten shader still fails, it falls back to preserving the effect timing and sound trigger while skipping only the render, so the `Inspiration`/tuning card can continue resolving its selected gameplay effect without crashing. This addresses the repeated `Shader compilation failed: Error: shader version mismatch` crash at `ElectrocardiogramLoeweEffect.update(ElectrocardiogramLoeweEffect.java:64)`. Type: crash fix implemented by `JacketNoAnoKoElectrocardiogramCompatPatches`.

13. `JacketNoAnoKoJesterFormCompatPatches`
Reimplements JacketNoAnoKo's `JesterForm.use` and `JesterFormPower.atStartOfTurnPostDraw` on Android-compatible runtimes so the gameplay actions still apply while creation of `CombinedFireworksSpotlightEffect` is guarded. If the rewritten shader compiles, the original fireworks/spotlight effect is preserved; if shader setup still fails, only that visual effect is skipped. This addresses the `Shader compilation failed: Error: shader version mismatch` crash at `CombinedFireworksSpotlightEffect.<init>(CombinedFireworksSpotlightEffect.java:40)` when playing `jacketnoanokomod:JesterForm` or when its power triggers on later turns. Type: crash fix implemented by `JacketNoAnoKoJesterFormCompatPatches`.

14. `NativeTouchscreenAllowlistPatches`
Rewrites selected base-game reads of `Settings.isTouchScreen` so the launcher's native touchscreen compatibility allowlist can switch between two runtime modes: `vanilla_allowlist`, which hides global touchscreen semantics from mods and only restores verified vanilla touch-confirm flows, and `global`, which falls back to the original native touchscreen behavior. In allowlist mode the patch keeps the touch indicator plus the vanilla shop purchase, card-reward selection/confirm, combat targeted-card dragging/release, and boss-relic confirm paths available when launcher touch input is enabled, but leaves most mod code on desktop-style semantics. Campfire option handling is intentionally left on desktop semantics because campfire buttons are a common mod extension point; native-touch confirmation for campfire actions is provided separately by `CampfireDesktopTouchConfirmPatches`. This addresses the symptom where enabling native touchscreen mode globally causes modded screens to enter untested confirm-button state machines or touch-only obtain flows, prevents vanilla card rewards from falling back to desktop direct-pick behavior in hybrid mode, and keeps targeted cards from entering the desktop single-target drag branch instead of canceling on touch release. Type: compatibility workaround implemented by `NativeTouchscreenAllowlistPatches`.

15. `TouchscreenButtonStateCleanupPatches`
Clears stale `Hitbox.clicked` and `Hitbox.clickStarted` state when common confirm/cancel/proceed/peek buttons are hidden or hidden instantly, while intentionally leaving their `show`/`showInstantly` paths untouched so an active press can survive until release. This addresses the symptom where touchscreen confirm buttons can re-fire on later frames or after screen transitions because the original click state was never consumed or reset by modded UI flows, without breaking vanilla buttons that repeatedly call `show()` while waiting for a click. It also clears the private `EndTurnButton` hitbox and long-press `holdProgress` when the end-turn button is disabled, hidden, or re-enabled, and keeps clearing those fields before `EndTurnButton.update()` while the original touch press is still down. This addresses the symptom where a touch press that ended one player turn can survive into the next turn and convert the later release or residual hold into an immediate extra end-turn. It also clears `SkipCardButton` hitbox click state when the card-reward skip button is hidden, shown, or returning from its one-frame `screenDisabled` state. This addresses the symptom where skippable discovery screens, including Attack/Skill/Power Potion choices, can consume the potion and close from a stale skip-button click before `CardRewardScreen.discoveryCard` is written, leaving no selected card to add to hand. The `EndTurnButton.disable(boolean)` postfix also avoids binding the unused boolean argument by name, preventing startup-time `PatchingException: Illegal patch parameter: No matching parameter with name "triggerEndTurn"` failures on runtimes whose target method parameter name is not available to ModTheSpire. Type: gameplay/runtime compatibility workaround and startup crash fix implemented by `TouchscreenButtonStateCleanupPatches`.

16. `MainMenuTouchLayoutCompatPatches`
Restores the large-button and large name-edit visuals that the vanilla main menu normally uses for touch/mobile presentation, but only inside the main menu's own layout branches. In `vanilla_allowlist` mode this keeps the home-screen buttons, name-edit hitbox, and save-slot prompt from shrinking back to desktop sizing just because global touchscreen semantics were hidden from mods, while still avoiding a full main-menu touchscreen interaction rollback. This addresses the symptom where enabling the native touchscreen compatibility allowlist makes the title-screen options noticeably smaller than before. Type: compatibility workaround implemented by `MainMenuTouchLayoutCompatPatches`.

17. `ExpectedGameExitPatches`
Writes the launcher's expected-exit marker before vanilla main-menu Quit and LibGDX `LwjglApplication.exit()` paths continue into native teardown. This addresses the symptom where an intentional game exit reaches `application_shutdown` but Android still records a native `SIGABRT` such as `FORTIFY: pthread_mutex_lock called on a destroyed mutex`, causing the launcher to show a crash recovery page on the next return. Type: crash-report false-positive fix implemented by `ExpectedGameExitPatches` and `ExpectedGameExitMarker`.

18. `DebugRuntimeCrashPatches`
Adds a debug-only runtime crash trigger controlled by the launcher's `amethyst.debug.force_runtime_crash` system property so device verification can confirm expected-exit suppression does not hide real gameplay/update crashes. It is inert in normal release configuration because the launcher only forwards the property from debug preferences. Type: diagnostic hook implemented by `DebugRuntimeCrashPatches`.

19. `TouchscreenSingleTargetCancelPatches`
Cancels the current combat targeted-card selection when a native touchscreen blank tap or release would otherwise promote an already selected targeted card into the base game's single-target mode or directly call `playCard()` with no hovered monster, and also cleans up any blank click/release that still returns from `AbstractPlayer.updateSingleTargetInput` in target-selection mode. This addresses the symptom where cards such as `Strike` can remain stuck in midair after tapping the card and then tapping empty combat space under the launcher's default hybrid touchscreen setting; tapping a monster, including a near-monster tap handled by `TouchscreenTargetAssistPatches`, is not intercepted and still continues through the target/play-card path. The launcher `Card play optimization` / `出牌优化选项` setting controls this through `amethyst.runtime_compat.touchscreen_card_play_optimization`: every optimized mode enables it, while `Vanilla behavior` disables this patch path. Type: gameplay/runtime fix implemented by `TouchscreenSingleTargetCancelPatches`.

20. `DisplaySettingsPromptCompatPatches`
Replaces the base game's display-settings restart prompt with a launcher-specific warning telling players not to change graphics quality in-game and to use launcher settings instead, keeps the warning visible with rhythmic pulsing text while the settings page remains open, and clears it when leaving the settings page. This addresses the symptom where changing quality-related options in the in-game settings shows the misleading vanilla message that a game restart is enough for display-setting changes to take effect, and where the warning can disappear before the player closes settings even though Amethyst-managed graphics options should be adjusted before launch. Type: compatibility workaround implemented by `DisplaySettingsPromptCompatPatches`.

21. `NativeTouchscreenAllowlistPatches` touch-indicator switch
Extends the existing `GameCursor.render` patch so the launcher can disable the native touch indicator without changing hybrid/mobile touch input semantics. This addresses the symptom where tapping the screen in hybrid touchscreen mode always shows the small fading circle from `GameCursor.render`, which is triggered after `InputHelper.updateFirst` raises `CardCrawlGame.cursor.color.a` on touch down. The launcher forwards `amethyst.touch_indicator_enabled`; when it is disabled the patch skips only the touch-indicator render path while leaving tap handling and allowlisted touchscreen flows intact. Type: compatibility workaround implemented by `NativeTouchscreenAllowlistPatches`.

22. `AndroidFilePickerBridge`
Provides a reusable launcher bridge from JVM-side compatibility patches to Android's native document picker. The JVM side writes a generic file-picker request with a MIME type, waits for the Android activity to copy the selected document into a JVM-readable temporary file, and returns that file to the calling compatibility patch. This addresses Android file-selection needs for desktop-oriented mods without patching `java.awt` classes directly, which the JVM rejects because `java.*` package instrumentation can fail with `SecurityException: Prohibited package name`. Type: generic bridge implemented by `AndroidFilePickerBridge` with Android-side handling in the launcher.

23. `CardImageReplacerFileDialogMimePatches`
Specializes the generic Android file-picker bridge for CardImageReplacer's in-game "Replace the card image" button by requesting `image/*` from Android's native document picker and then calling CardImageReplacer's own `FileChooserCallBack`, preserving its original resize, mask, save, reload, and popup-refresh behavior without modifying the third-party jar. This addresses CardImageReplacer's image replacement workflow while keeping the underlying file-picker bridge reusable for future mod-specific file-picker integrations. Type: mod-specific integration on top of the generic file-picker bridge implemented by `CardImageReplacerFileDialogMimePatches`.

24. `HandLayoutRoomContextRescuePatches`
Skips only `CardGroup.refreshHandLayout` when the current map node or current room is unavailable. This addresses null-context crashes seen during continue/start/reward flows where a card release refreshes hand layout before the room context has been restored. Normal hand-layout behavior is unchanged when a current room exists. Type: save-rescue crash fallback implemented by `HandLayoutRoomContextRescuePatches`.

25. `RoomTransitionRescuePatches`
Lets `AbstractDungeon.nextRoomTransition(SaveFile)` keep advancing toward the selected next room when the previous current-room context is already missing, and handles `AbstractDungeon.setCurrMapNode` without transferring souls from a missing previous room. This addresses crashes while entering the next room from corrupted current map-node or room state, while preserving the original transition path whenever the previous room is valid and keeping the original `AbstractDungeon.getCurrRoom` call shape available to other instrumentation patches. Type: save-rescue crash fallback implemented by `RoomTransitionRescuePatches`.

26. `EventRoomRescuePatches`
Wraps the `AbstractDungeon.generateEvent(...)` and `AbstractEvent.onEnterRoom()` calls inside the original `EventRoom.onPlayerEntry` method instead of replacing the whole method, so third-party insert patches that replace the generated event can still run. If event creation returns null, throws a null-context failure, or the event crashes with a null-context failure while entering, the patch marks the room complete and shows the proceed button. It also prevents a later `EventRoom.update` crash when the room's event field is already null. This addresses corrupted or exhausted event-room state that would otherwise crash on entering or updating the event room, and fixes the symptom where event-replacement mods such as Grimm Fairy Tales could not trigger their first-question-mark special event because the previous rescue prefix skipped their `EventRoom.onPlayerEntry` insert patch. Type: save-rescue crash fallback and compatibility fix implemented by `EventRoomRescuePatches`.

27. `ShopRoomRescuePatches`
Runs the normal shop-entry setup and merchant creation under a narrow null-context guard, then marks the shop room complete and shows the proceed button if `Merchant` construction fails because card-pool or room context is missing. This addresses corrupted shop saves where entering the shop would crash before the player can leave. Type: save-rescue crash fallback implemented by `ShopRoomRescuePatches`.

28. `BaseModSaveLoadRescuePatches`
Wraps BaseMod `CustomSavableRaw.onLoadRaw` calls during player-save loading and catches only `NullPointerException` from an individual custom save field. This addresses continue/load-save crashes caused by one mod's bad custom save payload while letting the rest of the save-load flow continue, and preserves the original `onLoadRaw` call shape for other BaseMod save instrumentation. Type: save-rescue crash fallback implemented by `BaseModSaveLoadRescuePatches`.

29. `RelicEnterRoomRescuePatches`
Wraps relic `onEnterRoom(AbstractRoom)` calls during room transitions and catches only `NullPointerException` from an individual relic hook. This addresses saves or mod states where one relic crashes while entering the next room, while allowing the transition and remaining relic hooks to continue and preserving the original `onEnterRoom` call shape for other relic transition instrumentation. Type: save-rescue crash fallback implemented by `RelicEnterRoomRescuePatches`.

30. `DungeonRenderRoomContextRescuePatches`
Skips only dungeon/player rendering frames while the current map node or room is unavailable. This addresses repeated render-loop null-context crashes from corrupted room state, without changing rendering once a valid current room is restored. Type: save-rescue crash fallback implemented by `DungeonRenderRoomContextRescuePatches`.

31. `PowerIconRenderRescuePatches`

34. `CardTooltipKeywordRescuePatches`

35. `RoomStateRescueNoticeBridge`
Provides the JVM-side notification bridge shared by the save-rescue fallbacks. Type: support bridge implemented by `RoomStateRescueNoticeBridge` with Android-side polling in the launcher.

36. `AutoplayPatches` / `AutoplayDriver`
Adds an opt-in autoplay driver, gated behind the launcher's `amethyst.debug.autoplay` system property and exposed through the Gradle `:app:stsStartAutoplay` task. When enabled, a `CardCrawlGame.update` postfix throttle-ticks an internal state machine that: (1) on the main menu, applies the configured save mode: the default `fresh` mode deletes stale autosave files for every player class once per autoplay JVM session, removes already-built Continue/Abandon buttons, opens the character-select screen, queues a native character-option click, and then presses Embark so autoplay starts a fresh run; `continue` mode keeps save files intact and presses Resume/Continue when available, falling back to a new run without clearing when no previous save is visible; fresh-run character selection prefers an unlocked `ORI` character option when present so Ori-only performance smoke runs cover the modded character render path instead of the first vanilla character; (2) in combat, plays a uniformly random `canUse`-passing card from hand against a random alive monster each tick, then calls `GameActionManager.callEndTurnEarlySequence()` when no card is playable; (3) on the dungeon map screen, picks a random reachable next-row node connected to the current node and submits it through the vanilla `DungeonMapScreen.clicked` plus hovered-node path; (4) on combat-reward, boss-reward, card-reward, grid, hand-select, transform, shop/treasure/neow rooms, and other proceed-ready states, presses the overlay proceed button to advance to the next room; (5) in campfire rooms and non-combat question-mark event rooms, marks the room complete, shows the proceed button, and presses it so autoplay skips those choice UIs directly without stalling on fire actions or event options. The driver short-circuits when the property is `false` (the default for every normal launch), catches `Throwable` from each tick so a runtime mismatch never crashes the engine, and only touches death-end screens to return autoplay to the main menu while leaving user-initiated settings/save-slot/victory screens alone. When the launcher also passes `amethyst.autoplay.wait_for_agent=true`, normal autoplay waits for `PlayMonitorAgent`; after the agent attaches, `AutoplayDriver` consumes queued agent commands and respects `COMMAND_DRIVEN` mode by suppressing autonomous decisions, addressing demo/debug sessions where the external harness must take deterministic control of card play and room progression. This also fixes an Android autoplay launch regression where `:app:stsStartAutoplay` could fail before the game opened because the Gradle adb task asked the device shell to resolve and splice the launcher component into `am start`; the build plugin now launches `io.stamethyst/.LauncherActivity` with structured adb arguments, and `stsStartAutoplay` depends on `stsStop` so each Gradle autoplay launch abandons any already-running game process before starting the next session. It also fixes the autoplay driver engaging but idling forever on the visible title menu when frame-id based throttling stops advancing or when `CardCrawlGame.mode` is not yet `CHAR_SELECT`; `AutoplayDriver` now uses monotonic wall time for tick throttling, and `AutoplayMainMenuActions` treats the actual `MainMenuScreen.CurScreen` as authoritative while still refusing to run during `GAMEPLAY`. It also fixes the symptom where deleting the old autosave after the main menu was built left a stale Continue button visible, and where manually setting `CharacterOption.selected` made the character-select portrait go black without actually starting a new game; `AutoplayMainMenuActions` now removes the stale resume buttons and routes selection through the vanilla character-option update path so `chosenCharacter`, portrait image, and Embark state are all initialized together. It also fixes the symptom where autoplay could start a fresh run but stall in the initial Neow room because that room hides the proceed button; `AutoplayDungeonActions` now treats `NeowRoom` as a skip-ready startup event, marks it complete, shows proceed, and lets the vanilla proceed path open the map. It also fixes the symptom where autoplay could play combat and skip rewards but never enter the next room from the map because `MapRoomNode.hb.clicked` is not consumed by the vanilla map; `AutoplayDungeonActions` now drives the map through the same hovered-node plus `DungeonMapScreen.clicked` selection path the game uses. It also fixes the symptom where autoplay leaves Neow but fails to enter the first combat because a freshly opened map can still have stale `MapRoomNode` hitbox centers; `AutoplayDungeonActions` refreshes the chosen node before moving input to the current hitbox center and submitting the vanilla map click, then falls back to the same direct `nextRoom`/path/transition state updates used by the vanilla node-selection completion path if the synthetic click is not consumed. It also fixes the symptom where autoplay reaches the top map row but never enters the boss fight because the boss icon is not a normal next-row `MapRoomNode`; `AutoplayDungeonActions` now drives the vanilla `DungeonMap.bossHb` plus `InputHelper.justClickedLeft` boss-entry path, verifies that `nextRoom` becomes a `MonsterRoomBoss`, and falls back to the vanilla boss-entry state update when the synthetic boss click is not consumed. It also avoids noisy startup-only tick warnings while a save is still loading and the dungeon has no current room or map-node context yet by treating those reads as temporarily unavailable and retrying on a later tick. Type: diagnostic/automation hook implemented by `AutoplayPatches`, `AutoplayDriver`, `AutoplayMainMenuActions`, `AutoplayDungeonActions`, `AutoplayEndScreenActions`, with configuration parsing in `AutoplayConfig` and shared logging in `AutoplayLog`; Gradle launch wiring implemented by `StsAndroidAppBuildPlugin`.

Map-entry guard update: fixes the symptom where the map opens after the skipped Neow room while the current Neow room still reports `EVENT`, causing both vanilla and direct first-node selection to reject. `AutoplayDungeonActions` now re-marks that startup room `COMPLETE` on the map screen before selecting row 0, so the first combat can transition.

Death-screen loop update: fixes the symptom where a long autoplay smoke session stops forever after the player dies because the driver previously left `DEATH` and death-origin `NEOW_UNLOCK` screens untouched. Hooked by `AutoplayPatches` through the driver, `AutoplayEndScreenActions` now queues the death screen's `ReturnToMenuButton` through both summary/stat clicks and confirms any death-triggered unlock screen, letting vanilla return to the main menu so `AutoplayMainMenuActions` can continue according to the configured save mode. Type: diagnostic/automation hook implemented by `AutoplayEndScreenActions`.

Autoplay save-mode update: adds `amethyst.debug.autoplay.save_mode=fresh|continue` so harness runs can choose between the existing destructive fresh-run behavior and a non-destructive resume of the previous save. This addresses automation/debug sessions that need to continue a prepared in-progress run instead of deleting it at the main menu. `AutoplayConfig` parses the mode, `AutoplayMainMenuActions` either clears stale saves and starts fresh or presses Resume/Continue while preserving save files, and `AutoplayDriver` logs the effective mode at startup. Type: diagnostic/automation hook implemented by `AutoplayConfig`, `AutoplayDriver`, and `AutoplayMainMenuActions`; launcher/harness wiring is implemented by `StsAndroidAppBuildPlugin`, `StsLaunchSpec`, and the Python harness.

37. `TouchscreenCardInputCursorPatches`
Replaces only the base game's combat-card `Gdx.input.setCursorPosition(...)` calls inside `AbstractPlayer.clickAndDragCards` and `AbstractPlayer.updateSingleTargetInput` with a native-touch-aware wrapper, leaving the calls intact for desktop, controller, and disabled compatibility modes. In native touchscreen combat this suppresses the vanilla card-inspect, card-switch, and single-target neutral cursor warps that move hover state away from the user's finger after a tap or release. This addresses the symptom where target selection can drift upward or to a synthetic neutral position on the next frame, making monster taps feel imprecise under the launcher's touch-to-mouse bridge. The launcher `Card play optimization` / `出牌优化选项` setting keeps this enabled for every optimized mode and disables it for `Vanilla behavior` through `amethyst.runtime_compat.touchscreen_card_play_optimization` plus `amethyst.runtime_compat.touchscreen_cursor_warp_cleanup`. Type: gameplay/runtime fix implemented by `TouchscreenCardInputCursorPatches`.

38. `TouchscreenCardDragGesturePatches`
Tracks the start and upward movement of a native touchscreen card drag in `AbstractPlayer.clickAndDragCards`, requires a real upward play gesture before a non-target card release in the drop zone can continue to the vanilla play path, and clamps the base game's private `touchscreenInspectCount` before release so a second tap does not automatically jump selection to another hovered hand card. This addresses the symptom where a light tap or short press on a card can be interpreted as an intentional play or can switch the inspected card because Android touch input arrives as mouse down/up frames while vanilla touchscreen logic also warps the cursor. The launcher `Card play optimization` / `出牌优化选项` setting keeps this enabled for every optimized mode and disables it for `Vanilla behavior` through `amethyst.runtime_compat.touchscreen_card_play_optimization` plus `amethyst.runtime_compat.touchscreen_card_gesture`. Type: gameplay/runtime fix implemented by `TouchscreenCardDragGesturePatches`.
It also writes a short-lived Android bridge marker while the same native-touch hand-card gesture is active and the launcher `Ignore long-press right click while playing cards` / `出牌时忽略长按右键` switch is enabled. The launcher input bridge checks that marker before converting a stationary long press into a right click, so holding a selected card no longer cancels the left-button card hold, while long-press right click remains available outside card selection or when the switch is disabled. 39. `LoadoutClassScanCachePatches`

Type: cache-hit performance mitigation implemented by `LoadoutClassScanCachePatches`.

Type: cache-hit performance mitigation implemented by `LoadoutBaseGameMonsterSkipPatches`.

42. `TouchscreenCardTapInspectPatches`
Optionally preserves an inspect-only hand-card hover state after a short native touchscreen tap, without leaving the card selected, dragging, or ready to play. This addresses the symptom where suppressing idle hand-card hover can make a tap immediately collapse the card instead of floating it out to show its normal card text and tooltip information. The patch records the hand card touched in `AbstractPlayer.clickAndDragCards`, keeps slight finger drift within the tap slop from moving the card away from its natural hover position, clears `isDraggingCard` after a tap release, keeps only that explicit inspected card treated as hovered by `AbstractPlayer.updateInput` and `AbstractCard.updateHoverLogic`, and clears the previous inspected card before a different hand card is tapped so only one card stays floated. It also removes the old inspected card from `hoveredCard`/`toHover` before refreshing hand layout, covering the symptom where tapping card B after card A can leave A visually floated until another card is selected because vanilla `CardGroup.refreshHandLayout` still sees A as the hovered card. While a card remains tap-inspected, the patch also reapplies vanilla `CardGroup.hoverCardPush(...)` both when the card first floats out and after later hand-layout refreshes, covering the symptom where the enlarged card can overlap neighboring hand cards instead of making room for itself. Touch inspect converts the base game's immediate hand-hover `current_y` and `drawScale` writes into `target_y` and `targetDrawScale` updates, and preserves the pre-hover scale across `AbstractCard.hover()`, so tapped cards float out and return through the original card lerp animation instead of snapping. It also clears the inspect state when the card is released, played, removed from hand, or when the player taps blank space. The launcher `Card play optimization` / `出牌优化选项` setting enables this for both `Keep card popped out on release` and `Tap card, then tap target` through `amethyst.runtime_compat.touchscreen_card_tap_inspect`, keeps it off for the default `Pop card back on release` mode, and disables the whole card-play group for `Vanilla behavior`; it still does not run for desktop, controller, non-hand card groups, or mod UI screens. Type: optional gameplay/runtime fix implemented by `TouchscreenCardTapInspectPatches`.
