# Ram Saver

## Low-overhead GPU diagnostics

`RamSaverDiag` is enabled only by the dedicated `ramsaver.diag.enabled=true` property. Deep performance diagnostics does not enable its intrusive render-thread stack capture, slow-event printing, verbose strings or repeat bookkeeping. Instead, deep diagnostics enables the separate `amethyst.gdx.resource_timings` recorder described in fix 43: every instrumented texture/FBO/region lifecycle operation is timed, with formatting and file I/O on a background thread. GPU counters, byte estimates and periodic summaries remain independent. Diagnostics-disabled launches allocate no timing recorder, queue, writer or thread-local timing state and take no additional lifecycle clock samples. Enabling complete recording adds CPU/storage work and can block when its bounded queue fills; this is the explicitly selected completeness-first policy, not a claim of zero-overhead baseline FPS.

This bundled mod carries Ram Saver's texture-lifetime changes as a launcher-managed ModTheSpire component, so the Android runtime can ship the same RAM-saving behavior and Amethyst-specific diagnostics without requiring a user-imported workshop jar.

## Included fixes

1. `com.badlogic.gdx.graphics.Texture`, `com.badlogic.gdx.graphics.RealTexture`, and `optispire.RamSaver`
Replace normal file-backed texture construction with fake/lazy textures that keep file identity and dimensions but defer real `RealTexture` creation until rendering or API calls need an actual GL handle. This addresses the symptom where heavily modded runs keep too many image assets loaded at once and exhaust Java/native/GPU memory. Type: memory-management workaround implemented by the Ram Saver texture replacement and asset manager.

2. `optispire.RamSaver`
Ages managed texture and atlas-region holders in small rotating buckets, disposes stale assets, and processes weak-reference notifications so logical image assets can be released after they are no longer strongly referenced. Type: memory-management workaround implemented by `RamSaver.update`, `ManagedAsset`, and the `FileTextureSupplier` path.

7. `optispire.patches.AggressiveGC`
Requests Java GC from selected lifecycle points to accelerate cleanup after Ram Saver has made assets collectible. This addresses the symptom where released fake/real texture wrappers can otherwise remain in heap until a later GC cycle. Type: memory-pressure workaround implemented by `AggressiveGC`.

This patch requires the launcher to leave explicit GC enabled. `RamSaver.update` drains a `ReferenceQueue` and only disposes a backing texture for entries the collector has already cleared and enqueued, so `System.gc()` here is what converts "collectible" into "native memory actually freed". The launcher therefore omits `-XX:+DisableExplicitGC` whenever Ram Saver is active (`StsLaunchSpec.resolveDisableExplicitGcEnabled`); with that flag applied these calls become no-ops and native texture release is deferred to the next incidental collection.

Because those calls are reachable, the launcher also adds `-XX:+ExplicitGCInvokesConcurrent` (`StsLaunchSpec.resolveExplicitGcInvokesConcurrentEnabled`, applied only when explicit GC was not suppressed, inside the 64-bit branch that selects G1). `System.gc()` otherwise defaults to a full stop-the-world collection, which lands on the render thread as a frame hitch; the G1 concurrent cycle still clears and enqueues the weak references this patch depends on, so the release path above is unaffected.

**Rate limiting (2026 performance fix)**: `AggressiveGC` now throttles `System.gc()` calls to at most one per 45 seconds (configurable via `ramsaver.gc.throttle_seconds`, range 10-300). This prevents multiple stop-the-world GC pauses during startup when BaseMod publishes cards/relics/characters/strings/keywords in quick succession. Suppressed GC requests are logged when diagnostics are enabled. This preserves Ram Saver's memory reclamation behavior while eliminating the 10-80ms frame drops that caused severe 1% low framerate degradation and user-visible stutter.

33. `optispire.RunTextureResidency`, `optispire.RamSaver`, and `optispire.patches.PlayerCardTextureResidency`
Protects the current player's master-deck images throughout the run and hand/draw/discard/exhaust/limbo/in-use card images during combat, including generated cards and bounded, cycle-safe card previews. Tracks instance texture/region fields and BaseMod small background/orb/banner resources, plus core card UI/orb atlas pages, without traversing static card libraries or loading large popup portraits. This addresses cards still owned by the player losing their real images after idle aging, hot-pin timeout, or unrelated hot-cache budget eviction, then synchronously decoding/uploading again when drawn. The scope-owned protection has no timeout, deduplicates texture configuration keys, and ends when the card leaves the tracked groups, combat-only cards are no longer needed, the player changes, the run ends, or gameplay is left. Withdrawal removes the old hot pin too and returns the texture to ordinary aging rather than deleting a currently visible image. Type: memory-management/rendering performance fix implemented by the listed classes.

Run residency is capped at **128 MiB** by default (`ramsaver.run.budget_mb`, 0 disables budgeted run protection, maximum 512), independently of the ordinary hot-cache budget (`ramsaver.hot.budget_mb`). This is not permission to retain the entire global card library. Admission retains the ordinary collection order: core UI, hand, draw/discard piles in their existing group order, master deck, then exhaust/limbo/in-use images. The draw prewarm gate still selects the actual upcoming cards separately; it does not reorder residency admission. Admission uses conservative RGBA estimates, includes mipmaps, and corrects estimates after upload; unknown-size textures stay lazy until a normal demand load provides dimensions. Admitted images may also receive ordinary hot pins, but run protection survives hot-pin expiry or eviction. Denied/withdrawn run images cannot bypass their budget through a hot pin. Current-hand ownership has a separate automatic-release exemption described in fix 42, including when this run budget is zero. These budgets bound speculative run protection, not total allocations: current-hand textures, visible demand loads and resources owned by other systems can exceed them.

At the tracked texture/FBO pressure threshold (default 512 MiB, or a lower configured GPU guardian soft budget; override with `ramsaver.run.pressure_mb`) or 90% Java heap use, budgeted run-owned protection yields and RUN decode/prewarm is canceled/paused. Current-hand automatic-release protection, unrelated hot pins and FIRST_COMBAT work remain independent. Recovery requires 30 seconds since the last high sample, tracked bytes below 80% of the threshold, and heap use below 80%. Pressure is sampled at most twice a second; clearing/changing the run resets its pressure state, and subsequent sampling can withdraw budgeted run protection again. Aging always retains the ordinary interval. These are tracked-resource safeguards, not an OS-wide available-RAM measurement; GPU/context loss or explicit mod disposal still requires restoration. Non-hand resources can still fall back to demand loading under pressure or for oversized decks. The existing texture-plus-FBO accounting is unchanged here, including the separately diagnosed overlap of FBO color bytes in both counters.

36. `optispire.RamSaver`
When enabled, routes all routine `update` reclamation through one incremental scheduler: weak-reference notifications, retired-parent child unlinking, and expired aging candidates share the same per-frame operation, estimated texture-byte, and elapsed-time limits. Aging buckets then only nominate candidates rather than deleting up to 48 additional textures outside the old reference-queue limit. This addresses post-GC/idle/pressure frame spikes caused by independent release paths accumulating work in one frame. Type: memory-management/frame-pacing fix implemented by `RamSaver.update`, `RamSaver.releaseAutomatically`, and `RamSaver.ManagedAsset`.

Shared automatic-release budgeting is opt-in (`ramsaver.release.shared_budget_enabled`, default **false**). With it OFF, reference/retired cleanup stays count-limited and aging buckets dispose directly. The following limits apply when it is ON (system properties are read once at startup):

- `ramsaver.release.max_per_frame`: **16 operations**, range 1–256. A texture release, a region unlink, a retired-parent completion, or a stale/cancelled notification check consumes a work slot; this also bounds CPU work when no GL deletion occurs.
- `ramsaver.release.max_bytes_per_frame`: **8388608 bytes (8 MiB)**, positive integer. Uses the real texture's conservative RGBA size estimate including mipmaps, not exact driver memory or the tracked texture/FBO counters. Region unlink work costs zero texture bytes. A candidate that would exceed the remaining allowance waits at the FIFO head; a texture larger than the whole allowance is allowed as the first texture deletion in a later frame, then further texture deletions wait. This avoids permanently stranding oversized assets.
- `ramsaver.release.max_micros_per_frame`: **2000 microseconds (2 ms)**, range 1–1000000. Checked between scheduler operations, including region/stale-reference work. At least one operation can progress per frame. **One GL delete cannot be interrupted** and may itself exceed the time cap; no later operation starts after the elapsed limit is observed. The bounded bucket scan (at most 48 entries) produces candidates before this release-time window; these limits are not a hard deadline for the entire render/update method.

The three sources rotate persistently across frames so reference or child-cleanup backlogs cannot starve expired textures, including when time permits only one operation per frame. Aging candidates are FIFO and deduplicated by the holder's reference identity (its generation); refresh and explicit disposal/replacement remove pending entries immediately, bounding candidate storage by currently loaded holders. Before execution the scheduler rechecks the active map entry, reference generation, retirement/freshness, and current hot/run protection (including a region's parent). A texture reused or newly protected while waiting therefore keeps its current handle rather than being deleted by an old candidate. The JVM reference queue is drained incrementally, without copying its backlog into another queue. Run pressure may withdraw run-owned protection, but never accelerates bucket visits, raises these release limits, or synchronously drains candidates.

Coverage boundary: the limits apply to routine reclamation in `RamSaver.update`, not explicit `RamSaver.dispose`, caller `Texture.dispose`, replacement of an existing generation during `loadTexture`/`loadRegion`, lookup-time invalidation of a region whose parent was already retired, context-loss/reload handling, or resources owned outside Ram Saver. These lifecycle operations retain their immediate semantics; deferred child cleanup they leave behind is budgeted on subsequent updates. Reference notifications clean only cleared regions (textures have a strong owner); neither region unlinking nor retired-child cleanup owns a GL texture handle.

Deterministic regression: `AutomaticReleaseBudgetTest` observes mock GL names/deletions, byte sums, resource reuse, injected-clock time, mixed-source progress, pressure release, oversized FIFO progress, protection changes while pending, and repeated replacement without obsolete-work buildup. An additional acceptance case drains 120 idle textures across three aging buckets while continuously binding one visible texture, checking every frame's release count and eventual completion without reloading the visible image. Its two initial count-limit tests failed on the old implementation (12 aging deletes in one frame; mixed cleanup exceeded the four-operation test cap). Background decode defaults and bounds:

Scope withdrawal, first-combat window expiry, run-only pressure withdrawal, explicit fake/real texture disposal, context invalidation/clear and application shutdown cancel relevant work.
