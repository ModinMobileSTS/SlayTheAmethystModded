# Ram Saver

## Low-overhead GPU diagnostics

`RamSaverDiag` is enabled only by the dedicated `ramsaver.diag.enabled=true` property. Enabling the launcher's Deep performance diagnostics no longer activates Ram Saver duration tracking, render-thread stack capture, slow-event logging, or per-resource lifecycle logging. This addresses the symptom where drawing or shuffling cards becomes visibly slower only while diagnostics are enabled, and prevents that diagnostic overhead from being recorded by the frame probe as a false gameplay stall. GPU texture/FBO counters, byte estimates, source attribution, and periodic summaries remain available; intrusive texture/FBO stack sampling, resource-stall timing, and lifecycle logs require their dedicated properties. The behavior is implemented by `optispire.RamSaverDiag`, with low-overhead defaults in `GLTexture` and `GLFrameBuffer`.

This bundled mod carries Ram Saver's texture-lifetime changes as a launcher-managed ModTheSpire component, so the Android runtime can ship the same RAM-saving behavior and Amethyst-specific diagnostics without requiring a user-imported workshop jar.

## Included fixes

1. `com.badlogic.gdx.graphics.Texture`, `com.badlogic.gdx.graphics.RealTexture`, and `optispire.RamSaver`

This addresses the symptom where heavily modded runs keep too many image assets loaded at once and exhaust Java/native/GPU memory. Type: memory-management workaround implemented by the Ram Saver texture replacement and asset manager.

7. `optispire.patches.AggressiveGC`
Requests Java GC from selected lifecycle points to accelerate cleanup after Ram Saver has made assets collectible. This addresses the symptom where released fake/real texture wrappers can otherwise remain in heap until a later GC cycle. Type: memory-pressure workaround implemented by `AggressiveGC`.

This patch requires the launcher to leave explicit GC enabled. `RamSaver.update` drains a `ReferenceQueue` and only disposes a backing texture for entries the collector has already cleared and enqueued, so `System.gc()` here is what converts "collectible" into "native memory actually freed". The launcher therefore omits `-XX:+DisableExplicitGC` whenever Ram Saver is active (`StsLaunchSpec.resolveDisableExplicitGcEnabled`); with that flag applied these calls become no-ops and native texture release is deferred to the next incidental collection.

Because those calls are reachable, the launcher also adds `-XX:+ExplicitGCInvokesConcurrent` (`StsLaunchSpec.resolveExplicitGcInvokesConcurrentEnabled`, applied only when explicit GC was not suppressed, inside the 64-bit branch that selects G1). `System.gc()` otherwise defaults to a full stop-the-world collection, which lands on the render thread as a frame hitch; the G1 concurrent cycle still clears and enqueues the weak references this patch depends on, so the release path above is unaffected.

**Rate limiting (2026 performance fix)**: `AggressiveGC` now throttles `System.gc()` calls to at most one per 45 seconds (configurable via `ramsaver.gc.throttle_seconds`, range 10-300). This prevents multiple stop-the-world GC pauses during startup when BaseMod publishes cards/relics/characters/strings/keywords in quick succession. Suppressed GC requests are logged when diagnostics are enabled. This preserves Ram Saver's memory reclamation behavior while eliminating the 10-80ms frame drops that caused severe 1% low framerate degradation and user-visible stutter.

33. `optispire.RunTextureResidency`, `optispire.RamSaver`, and `optispire.patches.PlayerCardTextureResidency`
Protects the current player's master-deck images throughout the run and hand/draw/discard/exhaust/limbo/in-use card images during combat, including generated cards and bounded, cycle-safe card previews. Tracks instance texture/region fields and BaseMod small background/orb/banner resources, plus core card UI/orb atlas pages, without traversing static card libraries or loading large popup portraits. This addresses cards still owned by the player losing their real images after idle aging, hot-pin timeout, or unrelated hot-cache budget eviction, then synchronously decoding/uploading again when drawn. The scope-owned protection has no timeout, deduplicates texture configuration keys, and ends when the card leaves the tracked groups, combat-only cards are no longer needed, the player changes, the run ends, or gameplay is left. Withdrawal removes the old hot pin too and returns the texture to ordinary aging rather than deleting a currently visible image. Type: memory-management/rendering performance fix implemented by the listed classes.

Run residency is capped at **128 MiB** by default (`ramsaver.run.budget_mb`, 0 disables run protection, maximum 512). This is a sub-budget of the shared texture protection policy, not permission to retain the entire global card library. Core UI, hand/in-use/limbo images, then draw-pile images in actual next-draw order take priority over discard/master-deck/exhaust resources. Admission uses conservative RGBA estimates, includes mipmaps, and corrects estimates after upload; unknown-size textures stay lazy until a normal demand load provides dimensions. Run candidates are never also charged or pinned in the generic hot cache. The shared protection allowance subtracts other tracked texture/FBO allocations from the aggregate pressure threshold (default 512 MiB, or a lower configured GPU guardian soft budget; override with `ramsaver.run.pressure_mb`). Run protection reserves bytes first and hot pins use the remainder, capped by `ramsaver.hot.budget_mb`. This bounds protection, not total allocations: visible demand loads and resources owned by other systems can still exceed it.

At the pressure threshold, generic hot pins and speculative prewarm yield first. Run protection is reduced in priority order to the remaining allowance targeting 80% of the threshold after reclaimable Ram Saver textures age out. At 125% of the threshold, 90% Java heap use, or five seconds of continuously sampled pressure, all run protection also yields. Recovery requires 30 seconds since the last pressure sample, tracked bytes below 80% of the threshold, and heap use below 80%. Pressure is sampled at most twice a second, including outside gameplay and with run protection disabled; changing players or leaving a run does not reset it. These are tracked-resource safeguards, not an OS-wide available-RAM measurement; GPU/context loss or explicit mod disposal still requires restoration. Under pressure or for oversized decks, demand loading and its possible stalls remain preferable to unbounded retention/OOM.

36. `optispire.RamSaver`
Routes all routine `update` reclamation through one incremental scheduler: weak-reference notifications, retired-parent child unlinking, and expired aging candidates share the same per-frame operation, estimated texture-byte, and elapsed-time limits. Aging buckets now only nominate candidates rather than deleting up to 48 additional textures outside the old reference-queue limit. This addresses post-GC/idle/pressure frame spikes caused by independent release paths accumulating work in one frame. Type: memory-management/frame-pacing fix implemented by `RamSaver.update`, `RamSaver.releaseAutomatically`, and `RamSaver.ManagedAsset`.

Automatic release defaults (system properties are read once at startup):

- `ramsaver.release.max_per_frame`: **16 operations**, range 1–256. A texture release, a region unlink, a retired-parent completion, or a stale/cancelled notification check consumes a work slot; this also bounds CPU work when no GL deletion occurs.
- `ramsaver.release.max_bytes_per_frame`: **8388608 bytes (8 MiB)**, positive integer. Uses the real texture's conservative RGBA size estimate including mipmaps, not exact driver memory or the pressure policy's tracked-format accounting. Region unlink work costs zero texture bytes. A candidate that would exceed the remaining allowance waits at the FIFO head; a texture larger than the whole allowance is allowed as the first texture deletion in a later frame, then further texture deletions wait. This avoids permanently stranding oversized assets.
- `ramsaver.release.max_micros_per_frame`: **2000 microseconds (2 ms)**, range 1–1000000. Checked between scheduler operations, including region/stale-reference work. At least one operation can progress per frame. **One GL delete cannot be interrupted** and may itself exceed the time cap; no later operation starts after the elapsed limit is observed. The bounded bucket scan (at most 48 entries) produces candidates before this release-time window; these limits are not a hard deadline for the entire render/update method.

The three sources rotate persistently across frames so reference or child-cleanup backlogs cannot starve expired textures, including when time permits only one operation per frame. Aging candidates are FIFO and deduplicated by the holder's reference identity (its generation); refresh and explicit disposal/replacement remove pending entries immediately, bounding candidate storage by currently loaded holders. Before execution the scheduler rechecks the active map entry, reference generation, retirement/freshness, and current hot/run protection (including a region's parent). A texture reused or newly protected while waiting therefore keeps its current handle rather than being deleted by an old candidate. The JVM reference queue is drained incrementally, without copying its backlog into another queue. Pressure may accelerate bucket visits and withdraw protection through the existing policy, but never raises these release limits or synchronously drains candidates.

Coverage boundary: the limits apply to routine reclamation in `RamSaver.update`, not explicit `RamSaver.dispose`, caller `Texture.dispose`, replacement of an existing generation during `loadTexture`/`loadRegion`, lookup-time invalidation of a region whose parent was already retired, context-loss/reload handling, or resources owned outside Ram Saver. These lifecycle operations retain their immediate semantics; deferred child cleanup they leave behind is budgeted on subsequent updates. Reference notifications clean only cleared regions (textures have a strong owner); neither region unlinking nor retired-child cleanup owns a GL texture handle.

Deterministic regression: `AutomaticReleaseBudgetTest` observes mock GL names/deletions, byte sums, resource reuse, injected-clock time, mixed-source progress, pressure release, oversized FIFO progress, protection changes while pending, and repeated replacement without obsolete-work buildup. An additional acceptance case drains 120 idle textures across three aging buckets while continuously binding one visible texture, checking every frame's release count and eventual completion without reloading the visible image. Its two initial count-limit tests failed on the old implementation (12 aging deletes in one frame; mixed cleanup exceeded the four-operation test cap). Tests use four operations/frame and the production 8 MiB/2 ms defaults, with a controllable scheduler clock rather than wall-clock sleeps. Existing `TexturePressurePriorityTest` workload and assertions remain unchanged. `RamSaverBeforeAfterTest.canAgeFalseCannotBypassPinBudget` advances one additional frame so seven evictions can obey the shared four-operation test cap while retaining its original memory assertion. These checks verify scheduling and lifecycle contracts, not Android driver latency or FPS.

37. `optispire.BoundedTextureDecoder`, `optispire.PngTextureDecoder`, `optispire.TextureDecodeService`, `optispire.RamSaver`, `optispire.RunTextureResidency`, `com.badlogic.gdx.graphics.Texture`, `optispire.patches.PrewarmTextureRegistry`, `optispire.patches.CombatTexturePrewarm`, `optispire.patches.FirstCombatUiPrewarm`, `optispire.patches.FirstCombatPrewarmBudget`, `optispire.patches.PlayerCardTextureResidency`, and `optispire.patches.TextureDecodeLifecycle`
Move supported file reads, PNG inflate and scanline reconstruction into one daemon worker; upload already decoded pixels on the rendering thread. This addresses prewarm frames doing both compressed-image decode and GL upload synchronously. Non-combat run prewarm, upcoming-card draw prewarm, and the existing first-combat atlas/UI registries all use this path. A queued/running request remains pending until upload or a terminal synchronous fallback attempt, so first-combat indexes and run entries cannot silently skip unfinished work. Uploads retain the shared one-step / two-clean-updates cadence. A draw gate yields after **500 ms or 120 invocations**, whichever comes first, even if the worker or filesystem makes no progress; normal drawing then uses the existing synchronous demand path. These limits bound intentional deferral, not the latency of an individual GL call or fallback decode. Type: bounded memory/render-thread performance fix implemented by the listed classes.

Background decode defaults and bounds:

- `ramsaver.decode.enabled`: **true**. False uses the original synchronous materialization path. The switch is checked when requesting prewarm.
- `ramsaver.decode.staging_mb`: **96 MiB**, range 1–256, read when the worker is first created. Before any full decoded allocation, the worker validates the PNG header and reserves `4 × (width × height × 4) + 2 × width × channels + 128 KiB`. The conservative charge includes decoded heap bytes, two reconstruction rows, native upload Pixmap, format-conversion/downscale/software-mipmap temporaries, and fixed stream/inflater workspace. A 2048×2048 RGBA PNG fits the default allowance; larger images may fall back. This is a decoded/storage budget, not a compressed-file-size estimate. Pending, running, ready and borrowed-for-upload pixels keep their reservation until their ownership ends. Canceled running work retains its charge and slot until it actually exits.
- `ramsaver.decode.max_pending`: **8 requests**, range 1–64, read at worker creation. Includes queued/header-probing/ready/failure records, canceled work still running, and active upload leases. Identical configuration keys merge (including run/first-combat scope ownership). There is at most one executor pump, never one unbounded executor task per texture. A full request/byte budget applies backpressure; render never waits for a Future. Header probing has fixed small scratch space even before reservation; compressed chunks stream through fixed buffers and have a hard **64 MiB input limit**.
- Pressure accounting adds the staging reservation once to the tracked texture/FBO pressure input. It is neither GL allocation credit nor another run/hot pin. Heap percentage still observes actual JVM use independently. Pressure pauses new speculative requests and cancels queued/ready work. The conservative reservation can trigger pressure before all its bytes have actually been allocated; ordinary demand allocations remain outside this speculative cap.

Coverage and compatibility: the asynchronous decoder supports **non-interlaced 8-bit RGB/RGBA PNG**, all five PNG row filters, and multiple IDAT chunks. It validates chunk CRCs, header dimensions, zlib completion and scanline length. It preserves unpremultiplied byte values without applying gamma/color-profile transforms, matching the normal libGDX/stb path. JPEG, palette/grayscale/16-bit/interlaced PNG, tRNS/APNG, CIM/ETC/KTX and other formats, unknown/malformed dimensions, oversized reservations, disabled GL20, and custom `FileTextureSupplier` subclasses use the synchronous path. Probe/decode failure also falls back synchronously. Dimensions are checked again on the actual decode stream, so a changed file cannot bypass its reservation. This is deliberately a smaller supported set than native stb; it does not repack atlases or create a background GL context.

Native concurrency evidence: `build-deps/desktop.jar` reports libGDX **1.9.5**; bytecode shows `TextureData.Factory`/`FileTextureData.prepare` constructing `Pixmap`, `Pixmap` using `Gdx2DPixmap.load`, and `FileTextureData`'s constructor potentially checking GL20 and copying to power-of-two dimensions. The shipped ARM64 `app/src/main/jniLibs/arm64-v8a/libgdx.so` exports `Gdx2DPixmap_load`, `gdx2d_load`, `stbi_load_from_memory`, `stbi_failure_reason`, `gdx2d_set_blend` and `gdx2d_set_scale`. Upstream [1.9.5 gdx2d.c](https://github.com/libgdx/libgdx/blob/1.9.5/gdx/jni/gdx2d/gdx2d.c) contains process-global blending/scaling and lazy lookup tables; [its stb_image.h](https://github.com/libgdx/libgdx/blob/1.9.5/gdx/jni/gdx2d/stb_image.h) contains global failure/flip/unpremultiply state. A single new worker does not serialize other mods' native callers, so this implementation **never invokes libGDX native Pixmap, TextureData.Factory, GL or RamSaver state on the worker**. It uses Java scanline code and a private `Inflater` (ended in `finally`); short-lived native Pixmaps and `FileTextureData` are constructed only by the render-thread uploader. The symbol inspection does not prove the deployed native binary is byte-for-byte upstream; the design needs no such assumption.

Lifecycle: a ready result is borrowed by the existing `FileTextureSupplier.get` path, which preserves the texture key, requested format, mipmaps, sampler and saved GL binding. `FileTextureData` remains managed and file-backed for normal synchronous context reload; it retains no initial CPU pixels after upload. The lease and upload Pixmap are released on success and failure. A demand miss takes a ready result immediately or cancels its old generation before synchronous loading. Running completion can publish only into its original job object, so it cannot overwrite a later upload or replacement. Scope withdrawal, first-combat window expiry, pressure, explicit fake/real texture disposal, context invalidation/clear and application shutdown cancel relevant work. Cancellation is cooperative at PNG rows/chunks; an already blocked file read cannot be forcibly interrupted by this code, but keeps its bounded charge/slot and cannot block render or publish a canceled result. Shutdown requests executor interruption and does not join it on the GL thread.
