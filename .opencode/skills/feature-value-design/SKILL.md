# 业务价值设计

先读[共同约定](../feature-refactoring/references/handoff.md)。本阶段只研究、讨论和记录业务价值；
不修改生产代码或测试，不设计类、模块、技术接口和适配层。

## 输入与研究

确认功能范围、目标用户和已有材料。定向读取文档、典型入口与关键测试，必要时追踪
状态和副作用，以理解用户价值、外部约束、失败后果与旧问题。
不以源码顺序复述调用链，不要求全面枚举接口或生成一比一迁移表。
每个关键结论注明代码/测试依据，区分事实、推断与未知；旧测试也可能固化旧缺陷。

## 讨论与产出

形成简明业务能力说明：

- 为谁解决什么问题，成功结果及失败影响是什么。
- 有意义的能力及典型场景，区分核心价值和历史实现机制。
- 提议保留、改变、取消及待定的行为，说明原因和兼容约束。
- 可观察的输入、结果、关键副作用、正常/边界/异常验收场景及明确不做的内容。

允许旧机制合并、拆分和取消，不因旧实现存在就要求保留。
只讨论业务边界，不把类结构、技术依赖和接口选择混入已确认业务契约。
与人类讨论分歧并获得明确确认；草案或未回答的问题不能视为接受。
若用户仅要求研究，交付研究结果和待确认问题，不擅自推进确认或实现。

## 完成与交接

业务能力、保留/变更/取消决定和验收场景经人类确认后，本阶段才标记完成。
交接说明、证据、确认来源及未知项，结束后停止。建议下一阶段为
`feature-isolated-implementation`，但本阶段不授权启动它。
