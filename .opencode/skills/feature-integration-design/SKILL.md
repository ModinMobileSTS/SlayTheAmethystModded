# 接入设计讨论

先读[共同约定](../feature-refactoring/references/handoff.md)。本阶段研究与设计，
不修改生产代码或测试，不提前接入或删除旧逻辑。

## 输入与调查

核对确认的业务契约、独立实现及实际验证证据；缺少必要证据时标明阻塞项。
围绕新能力调查真实入口、调用方、生命周期、状态/数据、副作用、资源和共享依赖。
接口与测试盘点在这里服务于实际切换，不作为独立阶段，不要求逐函数对应。
不能只做名称搜索就断定无调用；考虑项目实际采用的注册、配置、反射及其他动态入口。

## 与人类确认

- 新接口是否满足实际场景；调用方和装配需要哪些改动。
- 状态所有权、存量数据兼容、错误传播、取消/重入和资源释放等实际相关约束。
- 如何证明真实入口调用新能力；哪些针对性集成检查在接入阶段完成。
- 哪些旧路径先停用后删除，哪些共享能力保留，以及证据与理由。
- 接入后旧代码暂留的范围与期限（以清理阶段为目标），临时适配和回退是否确有必要。
  默认不添加静默回退；例外必须明确批准并写明退出条件与清理验证。
- 中间状态约束、最终回归范围、清理前提和失败时的处理边界。

产出按共同约定组织的接入与清理清单，包含测试处置及覆盖去向。
用户数据迁移或删除需单列影响与授权，不能混入代码清理。
设计改变业务能力时返回价值设计讨论；重大技术调整也需确认后才能实施。

## 完成与交接

清单和接入方案须由人类明确确认。建议、草案和“测试通过”不能代替确认。
仍有范围问题时列明，不提前执行对应修改。交接确认依据、调查证据和验收检查，
结束后停止；下一阶段是 `feature-integration`。
