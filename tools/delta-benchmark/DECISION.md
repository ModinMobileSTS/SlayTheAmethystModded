# 差分引擎选型：使用 HDiffPatch

决策日期：2026-11-14。用户根据 Android 实测确认：**使用 HDiffPatch**。
这是后续实现的算法选择，不是生产发布授权，不引入双引擎策略。

## 采用的能力

- 固定源码：`sisong/HDiffPatch`，commit
  `06961361340085ddb2a551775dc402172b8ca67c`；许可及内嵌归属见 NATIVE_SOURCES.md。
- 默认采用文件流式生成与应用，单线程，match block 64 B、step 256 KiB。
- 测试入口：`create_single_compressed_diff_stream` /
  `patch_single_compressed_diff`。通用差分不依赖 ZIP/JAR，归档作为输入/输出组件。
- 当前分发对照配置为外层 raw DEFLATE level 6；内部插件未启用。采用 HDiffPatch
  不代表已决定永远保留这个两遍压缩封装，格式与流水线仍需后续实现设计。
- 默认保留完整替换能力；差分收益不足时不强制使用差分。尚无经过验证的预判阈值。

## 选择依据

1. 在有界文件流式测试中，插入、移动、稀疏修改表现稳定；不会因固定位置比较而将
   插入之后的全部内容当作变化。16 MiB 移动样本原始补丁仅47 B。
2. 64 MiB 压缩流式样本，插入补丁39 B，稀疏修改3727 B；完全不同内容的生成约
   5.93秒，低于当前 xdelta 流式配置约31.04秒，但仍应避免无收益差分。
3. 256 KiB 与1 MiB step 对照未体现稳定的增大收益，选较小默认步缓存。
4. 对当前真实原始 JAR，xdelta 补丁略小，但 HDiff 生成更快，应用差异不足以支持
   增加第二套生产引擎。真实样本仅来自同一库，不宣称普适性能排名。
5. JVM BSDiff 存在移动补丁被现有解码器拒绝的兼容性失败；原生 BSDiff 在本轮
   综合速度/补丁大小方面没有体现足以优先采用的优势。

## 可信程度与失败证据

设备报告 M2007J3SY、Android10/API29、arm64；NDK27，`-O3`，非debuggable。
原生库版本固定。生成、应用新进程执行，阶段内10ms RSS采样，输入摘要及目标逐字节
核对。Android 电池温度始终24.2°C、thermal0，可能为陈旧/受限遥测，不能保证
CPU温控归一化或排除虚拟化/设备环境影响；结果仅证明此测试环境。

- 0.3：135配对129成功、6失败（JVM移动）；16 MiB54/54、真实JAR36/36通过。
- 流式初轮72/72通过，但 xdelta 小源窗口效果差，不是算法通用结论。
- 32 MiB搜索/64 MiB分配预算：18生成失败；后续诊断确认64 MiB表申请超预算。
- 单块缓存筛选只完成3成功/2失败，第6任务超时，不是完整18项。
- 修正有界 LRU 后54/54通过；64 MiB压缩流式20/20通过。
- 输出及分配限额注入16项通过（10+6），不等价真实ENOSPC/进程恢复。

## 实现前/上线前尚需完成

**必须保留的限制，不随算法选型自动关闭：**

- HDiff生成器的总内存硬上限尚未实现；step缓存不等于总内存。
- 测试用128 MiB文件/展开限制不是聚合磁盘配额，也不是最终产品要求。
- 当前压缩封装需要raw临时补丁，未验证断进程后清理/恢复、真实ENOSPC或恶意补丁模糊测试。
- 主机120秒超时不是原生执行截止时间；需可靠停止和现场保留协议。
- 增加更多游戏/模组的真实版本族；归档条目流的结果不证明可精确重建归档。
- 候选发布、原文件保护、历史引用和长期回退由Delta内容事务负责，算法不提供。

后续先实现上述边界内的 HDiffPatch 适配与验证；**不再将算法选择作为未决事项**。
